# 18 — Seed Data & Demo Scenarios

Seed data is generated by a deterministic script (`backend/…/seed.py`) so the demo is reproducible: fixed ids, fixed `SYSTEM_TIMEZONE`, fixed adapter outcomes for the scripted borrowers. All amounts are integer cents; all schedules are solved to sum exactly to their commitment ([07 §7.3](./07-financial-rules.md)).

## 18.1 Seed volumes (minimum)

| Entity | Count |
|--------|-------|
| Employers | 4 |
| Borrowers | 20 |
| Loans | 20 |
| Benefit agreements | 20 |
| Contributions | **full solved schedule** (all `termMonths` installments, Σ == commitment — activation generates the whole schedule) per agreement, with **~12 months of elapsed history** for mature agreements; every ACTIVE agreement seeded with `acceptingPayments: true` |
| Posted contributions | ≥ 10 across the scripted-scenario accounts (exclusive of the completed/near-complete agreements' backdated history, which alone carry a term's worth of posted rows) |
| Failed contributions | 4 |
| Retry-pending contributions | 3 |
| Open exceptions | 5 |
| Terminated employees | 2 |
| Completed benefit agreement | 1 |

Also seed the demo users (one per role) with the correct **custom claims** set, so login-as-role works in the demo ([12](./12-auth-and-security.md)). **Pinned demo credentials** (used verbatim by Playwright and the demo script): `ops@demo.test`, `mgr@demo.test`, `admin@demo.test` — shared fixed password set by the seed. Scripted adapter outcomes are driven by the seed-only `contribution.simulatedOutcome` field ([09 §9.5](./09-payment-processing.md)). A nightly `reset-demo` job re-runs the seed so the public demo self-heals ([14 §14.2](./14-async-and-background-jobs.md)).

## 18.2 Required demonstration scenarios

Each scenario is a specific seeded account that shows one behavior. The adapter is configured to produce the scripted outcomes deterministically ([09 §9.5](./09-payment-processing.md)).

1. **Healthy active account** — active benefit, several posted contributions, upcoming scheduled ones, clean timeline.
2. **Failed contribution awaiting retry** — a `FAILED` contribution with an open `PAYMENT_FAILED` exception (`occurrenceCount: 1`), ready to demo retry→post→resolve.
3. **Terminated employee with future contributions canceled** — one of the 2 terminated employees, benefit `TERMINATED`, past `POSTED` intact, future `CANCELED`, a `FUTURE_CONTRIBUTIONS_CANCELED` event.
4. **Repeated payment failure** — a contribution whose adapter outcome is always `SERVICER_UNAVAILABLE`; its single `PAYMENT_FAILED` exception shows `occurrenceCount ≥ 4` on one row (demonstrates the deterministic-exception upsert, not duplicate rows — a payment failure always upserts `{contributionId}__PAYMENT_FAILED` regardless of failureCode, [09 §9.3](./09-payment-processing.md)). Separately, seed **one standalone `SERVICER_SYNC_FAILURE` exception** (from the simulated sync job) so that type is represented in the workbench.
5. **Benefit approaching completion** — an agreement with `remainingCommitmentCents` near 0 (surfaced by the `status + endDate` index) to demo the `COMPLETED` transition.
6. **Payment protected by idempotency** — a scripted flow where the same `Idempotency-Key` is submitted twice; the second returns the identical result and **no** second attempt/posting is created (the crown-jewel behavior, visible in the timeline + attempts list).
7. **Employer with several active employees** — one employer with a cluster of active borrowers, to show the employer summary and portfolio rollups.
8. **Loan balance lower than the next scheduled contribution** — a nearly-paid-off loan where the final contribution is **balance-capped**: `postedAmountCents < scheduledAmountCents`, loan → `PAID_OFF`, remaining installments canceled, `BENEFIT_COMPLETED` ([07 §7.4](./07-financial-rules.md)).

> **Change from v1 — scenarios aligned to the v2 mechanics.** Scenario 4 now demonstrates the *single upserted* exception with `occurrenceCount` (not duplicate exceptions); scenario 6 asserts no second attempt is created; scenario 8 exercises the corrected balance-cap + completion path. Seed schedules use solved installment amounts so scenario 5's "remaining reaches 0" is actually reachable.

## 18.3 Demo script (2-minute narrative)
The recorded demo walks: dashboard → open scenario 2 account → schedule retry → process → watch it post, balances update, exception resolve, timeline fill (critical path A) → then scenario 3 to show termination stopping future benefits (critical path B) → close on the dashboard reflecting the changes. Full script in `docs/demo-script.md`.
